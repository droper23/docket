# Docket — Threat Model

Scope: an application that reads a student's authenticated academic session and stores a
copy of their course/assignment data locally. Assessed before any browser extension or
native app exists — several rows describe mitigations that are architectural commitments
for Phase 2+, not yet-shipped code, and are marked as such.

| Threat | Attack surface | Mitigation | Residual risk |
|---|---|---|---|
| Password/credential theft | Any code path that could touch a LearningSuite/BYU password | Docket never asks for, stores, types, or transmits a password. Auth is entirely the student's own CAS/Duo flow in their own browser; Docket only ever reads a session they already opened. Enforced structurally — there is no password field anywhere in the codebase. | None from Docket itself. A student could still be phished by an unrelated fake login page — outside this app's control. |
| Stolen/replayed session | A malicious actor obtaining the extension's access to a live session (Phase 2+) | Extension will request the narrowest permission scope possible (LearningSuite's origin only, not "all sites"). Session data stays inside the extension's storage boundary; the spec here is to never pass raw cookies/session identifiers to the local data layer, dashboard, logs, or any network destination other than `learningsuite.byu.edu` itself. | Not yet implemented/auditable — this is a design commitment to verify once Phase 2 code exists, not a proven property yet. |
| Malicious/compromised LearningSuite page content | Announcement bodies, assignment titles, descriptions — anything rendered from LearningSuite into Docket's UI | The dashboard renders these as escaped text (`esc()` in `src/server/render.ts`), never as raw HTML/`innerHTML`. A malicious `<script>` in an assignment title cannot execute. | Low. Would need to audit any future rich-text/announcement-body rendering (currently only titles/summaries are shown) if HTML rendering is ever added — must keep escaping. |
| Malformed/unexpected LearningSuite response (shape drift, HTML error page instead of ICS, etc.) | `IcsConnector.getAssignments`, any future authenticated parser | Payload-shape check before parsing (`BEGIN:VCALENDAR` prefix) with retry/backoff; parse failures return a typed `ConnectorResult` error and leave existing local data untouched — never corrupt or wipe the store. Verified: `test/ics.test.ts` "ignores malformed VEVENT blocks... instead of throwing." | Ongoing — `ajax.php` is explicitly undocumented and the connector for it doesn't exist yet; every new authenticated parser must be built with the same fail-soft discipline and fixture tests, not assumed. |
| Local data store corruption / partial write | Crash or kill mid-`save()` | Atomic write: write to a temp file, then `rename()` — a crash can never leave a half-written `snapshot.json`. A read failure that isn't "file doesn't exist" throws loudly instead of silently resetting to empty. | Low. Single-file JSON has no built-in transactional multi-write guarantee beyond this — acceptable at current single-user scale. |
| Sync engine logic bug silently destroying data | The reconcile/missing-detection algorithm | **Concretely happened during this build**: an early version's missing-detection wasn't scoped per-course, and archived 297 of 457 real assignments on the very first sync against live data. Caught by testing against the real account (not just a demo fixture), fixed by adding an explicit `scope` field, and locked in with a regression test (`test/syncEngine.test.ts`). Records are *archived* (status flag), never deleted, even in the buggy version — so the failure mode was "hidden from view," not "destroyed." | Real, demonstrated risk class. Mitigation: any future connector or reconcile change must run against the live account (or a snapshot of it) before being trusted, not just synthetic fixtures — synthetic single-course fixtures did not catch this bug. |
| Over-broad browser extension permissions (Phase 2+) | Manifest `host_permissions` / `permissions` | Commitment: request LearningSuite's origin only, never `<all_urls>`, unless a specific feature is proven to need more — and if so, document why in the manifest's accompanying README. | Not yet implemented/auditable. |
| Sensitive data in logs | Any `console.log`/diagnostic output | No password/cookie/session field exists to log in the first place (see row 1). Diagnostics (`src/core/diagnostics.ts`) expose counts and timestamps only, never assignment titles, grades, or announcement bodies. | Low, but must be re-verified any time a new log line is added — no automated log-content scanner exists yet. |
| Supply-chain compromise via dependencies | `npm install` | Zero runtime dependencies by design — the ICS parser is hand-rolled specifically to avoid pulling in a general-purpose iCalendar library for a narrow, well-tested use case. Only dev dependency: `typescript` + its type definitions. | Low today. Re-evaluate if/when a browser-extension build toolchain or EventKit bridge introduces new dependencies — each addition should be a deliberate, justified decision, not a convenience default. |
| Enumerating other students' course schedules | The ICS endpoint has no auth — anyone who knows/guesses a `courseID` can fetch that course's public schedule | This is a property of LearningSuite itself, not a Docket design choice. Docket's own guardrail: never enumerate or guess course IDs — only ever fetch courses the student explicitly told Docket they're enrolled in (`data/courses.config.json`, populated during onboarding, never inferred). | Out of Docket's control to fix (it's LearningSuite's endpoint), but Docket does not make it worse. |
| Accidental public exposure of a student's real course data | `data/courses.config.json` / `data/snapshot.json` committed to a public repo | Both are `.gitignore`d; only `data/courses.config.example.json` (placeholder IDs) is tracked. The one real semester's data seen during this build was moved to `legacy/` and is excluded from git, never committed. | Depends on the student not force-adding an ignored file — worth a pre-commit reminder if this project grows contributors. |
| Institutional ToS / abuse-of-system concerns | Automated requests to `learningsuite.byu.edu` | ICS fetches are low-frequency (a few times a day at most, per student, for their own enrolled courses), read-only, and mirror what a subscribed calendar client already does. No load-testing, no scraping beyond the student's own data, no mutating calls performed outside of the one reverted test during research. | Low — reflects a single BYU support-documented feature (calendar subscription), used as designed. |
| Malicious page spoofing a bookmarklet's POST to Docket's local server | `/connect/learningsuite/import`, `/connect/learningsuite/import-assignments` — reachable by any page's JS the moment the server is running, not just the real bookmarklet | Both routes validate shape and size strictly before writing anything (array-of-object checks, per-field length caps, item-count caps — see `validateDiscoveredCourses`/`validateAssignmentRows` in `src/server/index.ts`) and reject anything malformed with no partial write. Worst case a malicious page could write garbage course *names* into local config — it cannot read anything back (these are one-way POSTs), cannot reach a LearningSuite session it doesn't already have, and cannot touch a password/cookie (none exists to touch). | Low. A local HTTP server with no auth is inherently trusting of "whatever's running on this machine" — consistent with the local-first threat model, not a new category of risk. Revisit if this server is ever bound beyond a trusted local/private network. |
| Server bound to 0.0.0.0 for phone access | Anyone else on the same Wi-Fi/LAN, or the same Tailscale network, can reach the dashboard and the import routes above | Deliberate tradeoff for the phone-access feature (`docs/ARCHITECTURE.md` §9) — binds to all interfaces so a phone can reach it, but never to the public internet, and both realistic paths (home/campus Wi-Fi, Tailscale's private mesh) are non-public by construction. The data exposed is the student's own already-none-too-secret schedule (course names, due dates) — comparable sensitivity to what the ICS feed itself already exposes with no auth at all (see the enumeration row above). | Real for anyone sharing that Wi-Fi/Tailscale network (e.g. roommates, a public/untrusted Wi-Fi network) — no authentication gates the dashboard itself. Acceptable for the current single-user, personal-network use case; would need real auth before being marketed as safe on genuinely shared/untrusted networks. |

## Non-goals (explicitly out of scope, not overlooked)

- Detecting or defending against a compromised student device — if the OS/browser itself
  is compromised, no client-side app on it can fully protect data. Standard OS-level
  hygiene is the student's responsibility.
- Defending LearningSuite's own endpoint design (e.g. the unauthenticated ICS URL having
  no secret token) — that's BYU's system, flagged here for awareness, not fixed by Docket.
